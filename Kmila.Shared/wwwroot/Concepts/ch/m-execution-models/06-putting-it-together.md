# 把它们组装起来

真实的设计通常在同一个 entity 里**同时**使用并发和顺序代码。下面的播放器里有一个小 entity，它包含两个部分：

1. 一个**半加器**——纯组合逻辑，写成两条并发赋值。没有时钟，也没有 process。
2. 一个 **4 位计数器**——顺序、带时钟的逻辑，写在一个带 `rising_edge(clk)` 的 process 里。

这两个部分并排住在同一个 `architecture` 里。它们用不同的执行模型，是因为在回答不同的问题：

| 问题 | 模型 | 为什么 |
|---|---|---|
| *此刻* `a` 与 `b` 的和是多少？ | 并发 | 没有记忆、没有时钟——纯粹的门。 |
| 下一个时钟节拍*之后*计数是多少？ | 顺序 | 需要一个寄存器，让状态在时钟沿之间保持。 |

## 水管和旋转门

同一个 architecture 里有两台工作方式不同的机器：

<div class="lesson-figure"><iframe src="/_content/Kmila.Shared/anatomia/exec-turnstile.html" title="半加器的水管和一个由时钟驱动的旋转门寄存器" loading="lazy" style="aspect-ratio:640/340"></iframe></div>

- **水管（并发）：** `a` 和 `b` 一变，水就流到 XOR 和 AND 模块，`sum` 和 `cout` 灯在同一个 delta 里更新——不需要时钟。
- **旋转门（顺序）：** `count <= count + 1` 只是准备好下一个值（在入口等待的 `0001` 卡片）。只有在 `rising_edge(clk)` 时它才通过——旋转门转动，面板翻转。

## 两种执行模型协同工作

按下播放，你会看到：

1. 输入 `a` 和 `b` 变化 → 半加器的两条并发赋值在同一个 delta 周期里**一起**触发。
2. 时钟上升沿到来 → 计数器所在的 process 被唤醒， `if rising_edge` 这道守卫让我们进入自增分支。
3. 计数器里的 `<= count + 1` 是信号赋值——它在 delta 结束时才提交。

> **为什么这在真实设计里很重要：** 你用过的每一颗 CPU 都是这样搭起来的。组合逻辑负责决定「答案会是什么？」，带时钟的寄存器负责决定「什么时候把它提交？」。掌握了这个切分，你就掌握了数字设计背后完整的心智模型。

## 拿不准时：用 process 还是并发？

- **没时钟？不需要记忆？** 用并发赋值。它们读起来更省心、推理起来更省心，综合出来就是组合门。
- **需要在时钟沿之间记住一个值？** 用带 `rising_edge(clk)` 守卫的 process。这就是寄存器、FSM、计数器、累加器等一切带状态的东西的写法。
