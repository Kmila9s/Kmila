# 順次：一度に一歩ずつ

`process` の本体の中では、VHDL はすでに知っている言語とよく似た動きをする。文は **ソース順に上から下へ** 実行され、行を動かせば結果が変わる。

ただし、みんなが引っかかる落とし穴がひとつある。**variable（変数）** と **signal（信号）** で振る舞いが違うのだ。

| 種類 | 構文 | 新しい値が現れるのはいつ？ |
|---|---|---|
| **variable** | `tmp := a + 1` | **すぐに。** 次の文は新しい `tmp` を読める。 |
| **signal** | `result <= tmp + b` | **デルタサイクルの終わり。** それまでは、読み取っても古い値が返る。 |

プレーヤーは両方を使う小さなプロセスをたどる。行 5 を実行した瞬間に `tmp` が更新されるのに、`result` は `process` を抜けた *後* まで変わらない、という点に注目しよう。

## メモ帳と郵便受け

**variable** は担当者のポケットのメモ帳のようなもの。4 行目や 5 行目が実行されると新しい数字がすぐに書き込まれ、次の行はもうそれを読める。**signal** は手紙のようなもの。`result <= tmp + b` は手紙（13）を送信トレイに入れるだけで、**郵便トラック**——δ で示したデルタサイクルの終わり——が来て配達するまで、`result` は U のまま。

## なぜこれが大事なのか

こう書いたとする：

```vhdl
result <= 1;
result <= 2;
```

C ならこの 2 行の後 `result` は明らかに `2` だ。VHDL では？ **最後の代入が勝つ** — ただしデルタが閉じたときだけ。`process` が走っている間、`result` はまだ古い値のままで、シミュレータは `<= 2` に置き換わる前に `<= 1` のトランザクションを黙って捨てる。

> **試してみよう：** 行 7 に進んで信号テーブルを見よう。`tmp` は `8` だが、`result` はまだ `U` のはずだ。もう 1 ステップ進めると、`process` 本体が終わった *後* に `result` が `13` に跳ぶのが見える。
