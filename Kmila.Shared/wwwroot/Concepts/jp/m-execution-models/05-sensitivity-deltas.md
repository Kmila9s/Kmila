# 感度リストとデルタサイクル

信号は「デルタサイクルが閉じるまで」更新されないことをすでに見てきた。次はそのルールから生まれる古典的な落とし穴の話だ。

**感度リスト (sensitivity list)** は `process` の後ろの `( … )` のこと。シミュレータに *これらの信号のどれかが変化したときだけこのプロセスを起こせ* と伝える。

**デルタサイクル (delta cycle)** はシミュレーション時間の最小単位だ。1 つのデルタサイクルの中では、信号への代入は新しい値を **予約するだけ** で、値そのものはデルタが閉じるまで現れない。その間に信号を読むと、**古い** 値が返る。

この 2 つのルールを重ねると、下記の罠が生まれる。プレーヤーは 2 つの信号代入を持つ小さな `process` を走らせる。

```vhdl
process(a, b)
begin
  out1 <= a;
  out2 <= b and out1;   -- ← ここは何を読む？
end process;
```

無害に見える。学生はたいてい「行 3 で `out1 = a` にして、行 4 で `out1` を読んで `b` と AND する」と思う。でも行 4 が読むのは **古い** `out1` だ — 行 3 のトランザクションはまだ確定していない。

プレーヤーを見ると、`a` と `b` が両方 `1` なのに `out2` が `U` のまま出てくる。初めて見ると驚くはずだ。

## ドアベル

process は部屋のようなもので、担当者はドアベルが鳴るまで **眠っている**。どの signal にドアベルを付けるかは **感度リスト** が決める。

- `process(a, b)` では `out1` に **ドアベルがない**（線は空のソケット ✕ で終わっている）。4 行目が実行されると担当者は `out1` を読むが、見えるのは **古い** 値の U。その後 `out1` は 1 になるが誰も起きないので、`out2` は U のまま。
- `process(a, b, out1)` のボタンをクリックしよう。今度は `out1` のベルが鳴り、process がもう一度実行されて `out2` が 1 になる。これが下の方法 B だ。

## 直し方は 2 通り

### 方法 A — variable を使う

variable はすぐに更新されるので、次の行で `tmp` を読めば代入したばかりの値が得られる。

```vhdl
process(a, b)
  variable tmp : std_logic;
begin
  tmp  := a;
  out1 <= tmp;
  out2 <= b and tmp;   -- 新しい tmp を読む — うまくいく。
end process;
```

### 方法 B — 2 回目のデルタを待つ

感度リストに `out1` を追加する。最初のデルタで `out1` が確定した後、`process` は 2 度目に目覚めてもう一度走る。

```vhdl
process(a, b, out1)
begin
  out1 <= a;
  out2 <= b and out1;   -- 2 度目の起床で、確定した out1 を読む
end process;
```

どちらも動く。方法 A のほうがデルタ 1 個ぶん速く、データフローが明示的なので好まれることが多い。

> **試してみよう：** プレーヤーを 1 ステップずつ進めて信号テーブルを見よう。`a=1`、`b=1` でも `out2` は最終的に `U` になり、`1` にはならない。それが毎学期初心者を噛むデルタサイクルのルールだ。
