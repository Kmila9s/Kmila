# 組み合わせてみよう

実際の設計は、同じエンティティの中で並行コードと順次コードを **両方** 使う。以下のプレーヤーは、2 つの部品を持つ小さなエンティティを扱う。

1. **半加算器** — 2 つの並行代入で書かれた純粋な組合せ回路。クロックも `process` もない。
2. **4 ビットカウンタ** — `rising_edge(clk)` を使った `process` の中で書かれた、順次かつクロック付きのロジック。

両方は同じ `architecture` の中に隣り合って存在する。答える問いが違うので、違う実行モデルを使うのだ。

| 問い | モデル | なぜ |
|---|---|---|
| `a` と `b` の和は *たった今* 何？ | 並行 | メモリなし、クロックなし — 純粋なゲート。 |
| 次のクロックエッジ *の後* のカウントは？ | 順次 | クロックエッジ間で状態を保持するレジスタが必要。 |

## パイプと回転ゲート

同じ architecture の中に、働き方の違う 2 つの機械がある：

<div class="lesson-figure"><iframe src="/_content/Kmila.Shared/anatomia/exec-turnstile.html" title="半加算器のパイプと、クロックで動く回転ゲートのレジスタ" loading="lazy" style="aspect-ratio:640/340"></iframe></div>

- **パイプ（並行）：** `a` と `b` が変わると水が XOR と AND のモジュールに届き、`sum` と `cout` のランプは同じデルタで更新される。クロックは関係ない。
- **回転ゲート（順次）：** `count <= count + 1` は次の値（入口で待つ `0001` のカード）を用意するだけ。それが通過する——ゲートが回り、ボードが切り替わる——のは `rising_edge(clk)` のときだけだ。

## 2 つの実行モデルが手を組む

再生を押すと、こう見えるはずだ。

1. 入力 `a` と `b` が変化 → 半加算器の 2 行が 1 つのデルタサイクルで **一斉に** 発火する。
2. クロックが立ち上がる → カウンタの `process` が起き、`if rising_edge` のガードが通ってインクリメントに到達する。
3. カウンタの `<= count + 1` は信号代入 — デルタが閉じたときに確定する。

> **実際の設計でなぜ大事か：** これまで使ってきたすべての CPU は、この形で作られている。組合せ回路が「答えは何になるべきか？」を決め、クロック付きレジスタが「いつ確定させるか？」を決める。この分担をマスターすれば、デジタル設計の背後にある思考モデル全体を手にしたことになる。

## 迷ったら：process か並行か？

- **クロックが絡まない？ 記憶が要らない？** 並行代入を使おう。読むのも考えるのも軽く、組合せゲートに合成される。
- **クロックエッジ間で値を覚える必要がある？** `rising_edge(clk)` でガードした `process` を使おう。レジスタ、FSM、カウンタ、アキュムレータ — 状態を持つものはすべてここから生まれる。

プレーヤーは終端に達した。順次、並行、真の並列がなぜ当てはまらないか、感度リストの罠、そして 2 つのモデルの共存 — すべて見てきた。下からレッスンを完了にチェックしよう — 思考モデルはもう手に入っている。
