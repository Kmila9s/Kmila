# サンプル:推論される同期 ROM

すべての FPGA は **block RAM**(BRAM)を持っている — シンセサイザが、あなたのコードの中に ROM や RAM のパターンを認識したときに使う専用のメモリブロックだ。ベンダ固有のプリミティブをインスタンス化する必要はない。ツールがマップの仕方を知っている形で、プレーンな VHDL を書くだけだ。「推論(inference)」とは、その認識に付けられた名前だ:ツールはあなたの配列とプロセスを読み、あなたがメモリを意図したのだと *推論* する。

このサンプルは、移植性のある教科書的な ROM パターンだ。まともなシンセサイザ(Xilinx/AMD Vivado、Intel/Altera Quartus、Lattice Radiant、オープンソースの Yosys)はどれもこれを認識し、自動的に BRAM を割り当てる。

## このパターン

```vhdl
type rom_t is array(0 to 15) of std_logic_vector(7 downto 0);
constant ROM : rom_t := (
  x"00", x"01", x"04", x"09", x"10", x"19", x"24", x"31",
  x"40", x"51", x"64", x"79", x"90", x"A9", x"C4", x"E1"
);

process(clk)
begin
  if rising_edge(clk) then
    data <= ROM(to_integer(unsigned(addr)));
  end if;
end process;
```

これを BRAM フレンドリーな ROM にするポイントが 3 つある:

1. **ストレージが定数**(`constant ROM : rom_t := (...)`)。データは合成時に固定される。
2. **読み出しがクロック付き。** 組合せの ROM 読み出しは LUT にしかマップできない — 16 エントリの小さな ROM ならそれで構わないが、それより大きければ、シンセサイザに BRAM を割り当てさせるためにクロック付きのパターンが必要だ。
3. **`addr` を純粋にインデックスとしてだけ使う。** `addr` とメモリ参照の間に高価な組合せ論理がない。

## 組合せ vs 同期、そして読み出しレイテンシ

クロック付きの読み出しがすべての鍵だ。読み出しをただの並行代入として書くと —

```vhdl
data <= ROM(to_integer(unsigned(addr)));   -- 組合せ:分散 ROM(LUT)
```

— ツールは ROM を LUT で組み立てる(「分散」メモリ)。読み出しレイテンシはゼロだが汎用論理を消費し、スケールしない:数キロバイトの LUT-ROM は小さなデバイスを埋め尽くす。読み出しをレジスタに通せば(上の `process`)、ツールはテーブル全体を block RAM に落とし込め、はるかに高密度になる。

レジスタ付き読み出しの代償は **1 サイクルのレイテンシ** だ:あるエッジで `addr` を提示すると、`data` は *次の* エッジで現れる。これはバグではない — それが同期メモリを定義づける特徴であり、BRAM 内部の出力レジスタこそが、高いクロックレートでの設計のタイミングを満たすものだ。多くの FPGA は、2 サイクル目のレイテンシと引き換えにさらに良いタイミングを得るための、2 つ目のオプションの出力レジスタを提供している。

## アドレス幅は深さと一致させる

`to_integer(unsigned(addr))` は決して配列の範囲を超えてインデックスしてはいけない。16 エントリの ROM なら `addr` はちょうど 4 ビットであるべきだ。幅の広すぎる `addr` は範囲外のインデックスを生みかねず、シミュレーションで失敗し、合成後は予測不能に振る舞う。`2**addr'length = DEPTH` を保つか、インデックスをクランプ/ガードしよう。深さ、幅、アドレスサイズを結びつけておけば、全体が整合し続ける。

## なぜこの内容なのか?

この例の ROM は `n²`(`n = 0..15`)を保持している。小さなオペランドだけが必要なときには、完全な乗算器より速いルックアップテーブル方式の二乗ユニットとして便利だ。ほかにも次のようなものを格納できる:

- 正弦波テーブル(DDS 信号生成器用)
- CRC 多項式
- プロトコルのルックアップテーブル
- 文字フォント

ROM は実のところ、シリコンに凍結された真理値表にすぎない:アドレスビットの任意の組合せ関数を前もって計算して格納でき、論理をメモリと引き換えにしているのだ。

## サンプルが行うこと

シミュレーションは `addr` を 5 つの特定の値 0、1、4、8、15 で駆動する。クロックエッジの後、`data` は 1 サイクル遅れて対応する ROM エントリを表示する(これが同期 ROM の読み出しレイテンシだ — アドレスを尋ねると、データは **次の** クロックで返ってくる)。

## あなたの番

- **パラメータ化する。** 固定の 16 エントリサイズを `generic (DEPTH : integer := 16; WIDTH : integer := 8)` に置き換え、`addr` を `std_logic_vector(log2(DEPTH)-1 downto 0)` として大きさを決める。残りのコードはそのまま動くはずだ。
- **ファイルから内容を読む。** 実プロジェクトは、初期化関数か、定数の別 package 経由で ROM の内容を読み込む。hex 値のテキストファイルを VHDL に読ませてみよう(`std.textio` + `hread`)。配列を返す impure function の中で行えば、たいていのツールはそれをエラボレーション時に実行し、結果を BRAM に焼き込む。
- **2 つ目の読み出しポートを追加する。** シングルサイクル CPU の命令メモリ/データメモリのような用途に。このパターンは、カリキュラム後半の CPU プロジェクトで目にする。

## コースとのつながり

これは単元 IV *Memorias*(メモリ)だ:ROM ファミリ(ROM、PROM、EPROM、EEPROM、Flash)と、とりわけ *manejo de arreglos y diseño de memorias con lenguaje de descripción de hardware*(配列の扱いと HDL によるメモリ設計)。`type … array … of` の定数は、まさにこの単元が求める「配列の扱い」そのものだ。ファイル初期化の練習は、単元 V のファイル、関数、package を使う作業へと先取りして手を伸ばす。

## 覚えておくべきこと

- 推論とは、ツールが認識できる形でメモリを書くことだ — ベンダ固有のプリミティブは不要だ。
- クロック付きプロセスの中で **定数** 配列を読むのが、移植性のある同期 ROM のパターンだ。これは block RAM にマップされる。
- クロック付き読み出し = 1 サイクルのレイテンシと高密度な BRAM。組合せ読み出し = レイテンシゼロだが LUT を大量に食い、スケールしない。
- アドレス幅を深さに一致させ、インデックスが配列の端からはみ出さないようにしよう。
