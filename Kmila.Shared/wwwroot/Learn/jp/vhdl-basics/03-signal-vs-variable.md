# 信号(signal)と変数(variable)

これは VHDL で最も誤解されている区別だ。学生は「変数は C のローカル変数のようなものだ」と読んで、そのまま間違った方向へ全力で走り出してしまう。ここでしっかり地に足を着けよう。これを正しく理解できるかどうかが、*シミュレーションが通るだけ* のコードと、*意図したとおりのハードウェアになる* コードとを分けるからだ。

## VHDL には 2 種類の名前がある

VHDL には **信号(signal)**(architecture レベルで `signal` として宣言)と **変数(variable)**(process の中で `variable` として宣言)がある。どちらも値を保持でき、どちらも代入できる。しかし両者は **交換可能ではない**。

| | 信号 | 変数 |
|---|---|---|
| 宣言場所 | architecture(またはパッケージ) | process / サブプログラムの中 |
| 代入演算子 | `<=` | `:=` |
| 効力が及ぶタイミング | シミュレーションステップの終わり | 即座に |
| スコープ | architecture 全体で共有 | その process にローカル |
| モデル化するもの | 線(wire)やレジスタ | 一時的な計算 |

## 黄金律

- **信号への代入は *スケジュールされ*、その値は現在のシミュレーションステップの終わりに現れる。**
- **変数への代入は即座に、その行がある場所でそのまま起こる。**

これだけだ。信号と変数にまつわる「落とし穴」はすべて、この律の言い換えにすぎない。

## デモ

```vhdl
architecture demo of ex is
  signal s : integer := 0;
begin
  process(clk)
  begin
    if rising_edge(clk) then
      s <= 1;           -- スケジュール:s を 1 にする(まだ見えない)
      s <= 2;           -- スケジュール:s を 2 にする(最初のを上書き)
      -- ここで s は?  まだ 0。どちらの代入も効力を持っていない。
    end if;
  end process;
end architecture demo;
```

クロックエッジが完了した後、`s` は **2** になる。1 回の process 実行の中で信号が何度もスケジュールされたときは、*最後の* 代入だけが勝つからだ。process の中では、両方の代入の後でも `s` はまだ `0` のままだ。新しい値は process が終わるまで伝播しないからだ。

今度は変数で見てみよう。

```vhdl
architecture demo of ex is
begin
  process(clk)
    variable v : integer := 0;   -- 変数は process の中で生きる
  begin
    if rising_edge(clk) then
      v := 1;           -- 即座に効力を持つ
      v := 2;           -- 即座に効力を持つ
      -- v はここで、今この実行中に、2 になっている
    end if;
  end process;
end architecture demo;
```

2 つのことに注目しよう。

- 変数は `:=` を、信号は `<=` を使う。
- 変数は 1 つの process にローカルだ。別の process や並行代入から `v` を読むことはできない。

> 初期値について一つ細かな点がある。`variable v : integer := 0;` の `:= 0` は、シミュレーション開始時に **一度だけ** 実行され、process の実行ごとではない。変数は再代入しない限り、実行の合間でもその値を保つ。これこそが変数に *記憶する* 能力を与えているものであり、同時に、クロック付き process で書き込まれる前に読まれた変数が、うっかりレジスタを推論させてしまう理由でもある。

## これがハードウェアにとってなぜ重要か

信号は **線(wire)やフリップフロップをモデル化** する。線の値を同じ瞬間に 2 回変えることはできない。1 ステップの間に線を駆動したものが何であれ、そのステップの終わりには 1 つの値に落ち着く。

変数は process 内部の **一時的な計算をモデル化** する。シンセサイザはこれを、レジスタへ(あるいはレジスタから)つながる組合せ論理として実装するのが普通だ — あるいは完全に最適化して消し去る。

## 具体例:立っているビットを数える

変数は、ループの中で更新する中間結果が必要なときに真価を発揮する。

```vhdl
process(clk)
  variable ones : integer range 0 to 8;
begin
  if rising_edge(clk) then
    ones := 0;                      -- 実行のたびにアキュムレータをリセット
    for i in data'range loop
      if data(i) = '1' then
        ones := ones + 1;           -- 即座に更新し、次の反復で読み戻す
      end if;
    end loop;
    popcount <= ones;               -- 最終的な数を信号で公開する
  end if;
end process;
```

これを変数ではなく信号でやってみると壊れる。ループの中の `ones <= ones + 1` は 8 個の競合する代入をスケジュールし、最後の 1 つだけが生き残るので、いつも `0` か `1` にしかならない。このループには変数の *即座* のセマンティクスが必要なのだ。

## どちらを使うか

- **信号** — 既定の選択肢だ。あらゆるポート、あらゆるレジスタ、波形ビューアに表示されるあらゆるバスは信号だ。
- **変数** — 1 つの process の中のローカルなループカウンタや中間的な算術結果に使う。C のように「今書いたものをそのまま読む」セマンティクスが欲しいときだ。

## よくある罠

こう書く学生がいる。

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= b;    -- レジスタ 1
    b <= a;    -- レジスタ 2
  end if;
end process;
```

彼らは `a` と `b` が入れ替わらないのではと心配する。しかし信号への代入はスケジュールされるので、これは実際に **入れ替わる**。エッジで `a` は `b` の **古い** 値を受け取り、`b` は `a` の **古い** 値を受け取る。同時に、だ。これは実は、1 サイクルで 2 つのレジスタを入れ替える定石だ。

ところが変数に切り替えると、セマンティクスが変わる。

```vhdl
process(clk)
  variable a, b : integer;
begin
  if rising_edge(clk) then
    a := b;    -- a は今 b と等しくなる
    b := a;    -- b は新しい a を受け取る — つまり b は古い値を保ち、a が変わる
  end if;
end process;
```

入れ替わらない。両方とも古い `b` の値になってしまう。見た目がそっくりなコードなのに、結果は正反対だ — すべては黄金律のためだ。

## 覚えておくべきこと

- `signal`:値はスケジュールされ、ステップの終わりに現れる。`<=` で代入。線やレジスタをモデル化。architecture 全体で共有。
- `variable`:即座に更新される。`:=` で代入。process にローカル。中間的な計算をモデル化。
- 1 回の実行で複数回の信号代入 → 最後の 1 つが勝つ。複数回の変数代入 → すべてが順番に実行される。
- 迷ったら信号を使おう。
