# デルタサイクルと競合状態

シミュレータは、「2 つのことが同時に起こる」という状況に、決定的な順序を与えなければならない。VHDL の答えが **デルタサイクル(delta cycle)** だ。これは、壁の時計を進めることなく原因と結果を切り分ける、無限に小さな時間の一片だ。VHDL 標準のシミュレーションサイクルで正確に定義されており、これを理解することが、テストベンチの「奇妙な」振る舞いを突然腑に落ちさせてくれる。

## デルタサイクルとは何か

シミュレーション時間は実際のステップ(ns、µs、ms で測られる)で進む。しかし 1 つの時間ステップの中では、変化は **デルタサイクル** の順序で起こる。

- δ₀:ある代入が信号の更新をスケジュールする。
- δ₁:更新が効力を持つ。その信号に感度を持つ process は、新しい入力を見て起きる。
- δ₂:起きた process が *自分の* 更新をスケジュールする。
- δ₃:それらの更新が効力を持ち、さらに別の process が起きるかもしれない。
- …

各デルタは「実時間ゼロ」だが、それでも 1 つの因果ステップを表す。シミュレータは、もうどの信号も変化しなくなる — 回路が **安定する** — までデルタを回し続け、そのときはじめて実シミュレーション時間が次のイベントへと進む。

## シミュレーションサイクルを、もう少し正確に

エンジンの 1 周は次のとおりだ。(1) 次にスケジュールされたイベントまで時間を進める。(2) 今の時刻にスケジュールされたすべての信号を更新する。(3) それらの信号のいずれかを待っていたすべての process を、最後まで実行する(これが新しい更新をスケジュールすることがある)。(4) それらのうち *現在の* 時刻向けのものがあれば、もう 1 回デルタサイクルを行う。なければ時間を進める。ステップ 2 の信号更新は、ステップ 3 でどの process がそれを読むよりも *前に* すべて起こる — これが「信号はステップの終わりに更新される」という仕組みの正体だ。

## なぜこれが存在するのか

同じクロックエッジで両方とも更新される 2 つの信号を考えてみよう。

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= x;
    b <= y;
  end if;
end process;
```

デルタサイクルがなければ、シミュレータは恣意的な順序を選ばなければならない — `a` は `b` より先に更新される? それとも後? デルタサイクルはこれを回避する。両方の代入は δ₀ でスケジュールされ、両方とも δ₁ で効力を持つ。`a` や `b` を読む process は、どれも 2 つの新しい値を一緒に見る。結果はもう、シミュレータがたまたまものごとを訪れる順序には依存しない。

## データフローの連鎖

```vhdl
process(a)
begin
  b <= a;
end process;

process(b)
begin
  c <= b;
end process;
```

`a` が変わると、最初の process が発火して `b` をスケジュールする。次のデルタで `b` が新しい値を持ち、それが 2 つ目の process を起こし、それが `c` をスケジュールする。そのさらに次のデルタで `c` が正しくなる。`c` が `a` に追いつくのは **2 デルタサイクル** 後であることに注目しよう — 実時間は一度も動かないのに、因果関係は順序どおりに保たれた。ファイル内で 2 つの process を入れ替えても何も変わらない。デルタの順序付けが同じ最終結果を保証する。これこそ、デルタサイクルが存在する理由だ。

## 競合状態の罠

問題が起こるのは、**信号** のセマンティクスに「同じティックの中で、これはあれより先に起こるはずだ」という思い込みを混ぜたときだ。

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= b + 1;     -- a はステップの終わりに更新される
    b <= a + 1;     -- b は古い a を読む
  end if;
end process;
```

「1 行目が先に実行されるから、2 行目が実行されるときには `a` はもう更新されている」と思い込んでいたなら、それは間違いだ。両方の右辺は **古い** 値を使って評価され、その後で両方の結果がスケジュールされる。`b` は `a` の古い値を読むのであって、新しく計算された値ではない。

信号を変数に置き換えると、C スタイルの「今書いたものをそのまま読む」セマンティクスになる。

```vhdl
process(clk)
  variable aa, bb : integer;
begin
  if rising_edge(clk) then
    aa := bb + 1;   -- 即座に
    bb := aa + 1;   -- 新しい aa を見る
  end if;
end process;
```

これでソフトウェアプログラマが期待するとおりに動く。(そしてハードウェアは異なる。信号版は古いレジスタから並列に 2 つの加算器を作り、変数版は依存した連鎖を作る。)

## 古典的な実バグ:忘れられたエッジ

デルタ的な考え方は、このテストベンチの刺激がなぜ誤動作するのかも説明してくれる。

```vhdl
clk  <= not clk after 10 ns;
-- どこか別の場所、wait のない process の中で:
data <= next_value;   -- DUT がサンプルするエッジと同じデルタ?
```

刺激信号が、DUT がクロックする *同じ* デルタで変化すると、DUT が古い値を見るか新しい値を見るかは不安定になる。直し方は、刺激をアクティブエッジから安全なマージンだけ *離れた* ところで変化させることだ(あるいは `wait until rising_edge(clk)` の後に少し遅延を入れる)。「シミュレーションでは通るが順序がランダムに感じる」という報告の多くは、これにたどり着く。

## ツールでデルタを見つける

GHDL(Kmila が駆動するエンジン)も GTKWave も、デルタステップを見せてくれる — 1 つの時刻で、信号が最終値へ波及するのに数デルタサイクルかかることがある。波形に「時間ゼロ」を占めるグリッチが見えたら、それは中間的なデルタ値を見ているのであって、実際のハードウェアの振る舞いではない。

## 要点

- デルタサイクルは、偽の時間をでっち上げることなく並行論理を決定的にする、シミュレータのやり方だ。
- 信号への代入は現在のデルタの **後に** 効力を持つ。変数はそうではなく、即座だ。
- 右辺は *古い* 信号値で評価され、その後でスケジュールされる。
- テストベンチがクロックエッジ付近で「奇妙に」振る舞うなら、ツールを疑う前にデルタの順序付けの問題を疑おう。

## 覚えておくべきこと

- デルタサイクルは実時間ゼロでありながら 1 つの因果ステップだ。シミュレータは回路が安定するまでデルタを回し、それから時間を進める。
- 信号はデルタの合間に更新される(だから同じ実行の中では古い値を読む)。変数は即座に更新される。
- 競合を避けるため、テストベンチの刺激はアクティブなクロックエッジから離そう。
