# デルタサイクルと競合状態

シミュレータは「同時に起こる 2 つのこと」に決定論的な順序を与える必要がある。VHDL の答えは**デルタサイクル**:原因と結果を分ける、無限に小さい時間スライス。

## デルタサイクルとは

シミュレーション時間は実ステップで進む(ns、µs、ms 単位)。しかし 1 つの時間ステップ内では、変化は**デルタサイクル**順序で発生しうる:

- δ₀:信号更新をスケジュール。
- δ₁:更新が有効になる;その信号に感度を持つ process は新しい入力を持つ。
- δ₂:それらの process が自分の更新をスケジュール。
- δ₃:それらの更新が有効になる。
- …

各デルタは「実時間ゼロ」だが、因果ステップを表す。シミュレータは何も更新する必要がなくなるまでデルタを回り続け、そのときにようやく実時間が進む。

## なぜ存在するか

同じクロックエッジで両方更新される 2 つの信号を考える:

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= x;
    b <= y;
  end if;
end process;
```

デルタサイクルがなければ、シミュレータは恣意的な順序を選ばなければならない — `a` は `b` の前に更新?後?完全に同じ瞬間?デルタサイクルはこれを回避する:両代入が δ₀ にスケジュールされ、両方とも δ₁ で有効になる。`a` または `b` を読む process は、両方の新しい値を同時に見る。

## 競合状態の罠

これを見て:

```vhdl
process(a)
begin
  b <= a;
end process;

process(b)
begin
  c <= b;
end process;
```

`a` が変わると最初の process が発火し、`b` をスケジュール。δ₁ で `b` は新しい値。2 つ目の process が発火、`c` をスケジュール。δ₂ で `c` は正しい値。

ここで 2 つの process を入れ替えてみる。何か変わる?**変わらない**。デルタサイクルは、ファイル中の process の「順序」が違っても両経路が同じ最終結果になることを保証する。それがデルタサイクルが存在する理由。

## どこでうまくいかなくなるか

問題は **signal** 意味論と「同じ tick 内でこれをあれより先に起こしたい」を混ぜたとき。例:

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= b + 1;     -- a は tick の終わりに更新
    b <= a + 1;     -- b は古い a を読む
  end if;
end process;
```

「1 行目が先に動くから、2 行目では `a` がすでに更新されている」と仮定すれば、間違い。`a` は tick の終わりに更新される。`b` は古い `a` を読む。結果:両方とも古いデータを基に加算し、互いの新しいデータでは更新されない。

C 風意味論が欲しいなら signal を variable に置き換える:

```vhdl
process(clk)
  variable aa, bb : integer;
begin
  if rising_edge(clk) then
    aa := bb + 1;   -- 即時
    bb := aa + 1;   -- 新しい aa を見る
  end if;
end process;
```

これでソフトウェアプログラマが期待する通りに動く。

## まとめ

- デルタサイクルは、並行ロジックを決定論的にするシミュレータの方法。
- signal 代入はデルタサイクル**の後**で有効。variable は違う。
- テストベンチがクロックエッジ周辺で「変な」挙動をしたら、ツールのせいにする前に、まずデルタサイクル順序の問題を疑え。

カリキュラム次の練習では、小さな競合状態が実際に動いている。それを見つけ、名前を付け、修正する — もう二度とルールを忘れない。
