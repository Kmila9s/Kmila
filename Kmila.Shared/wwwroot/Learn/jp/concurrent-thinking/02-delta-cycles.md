# デルタサイクルと競合条件

シミュレータは「同時に 2 つのことが起こる」状況に決定的な順序を与える必要があります。VHDL の答えは **デルタサイクル** です: 原因と結果を分離する、無限に小さな時間のスライスです。

## デルタサイクルとは何か

シミュレーション時間は実ステップで進みます(ns、µs、ms で測られます)。しかし単一の時間ステップ内でも、変化は **デルタサイクル** 順に起こります:

- δ₀: 信号更新をスケジュールする。
- δ₁: 更新が有効になる; その信号に感度を持つプロセスは新しい入力を得る。
- δ₂: それらのプロセスが更新をスケジュールする。
- δ₃: それらの更新が有効になる。
- …

各デルタは「実時間ゼロ」ですが、因果ステップを表します。シミュレータは更新するものがなくなるまでデルタをサイクルし続けます — そのときはじめて実時間が進みます。

## なぜこれが存在するのか

同じクロックエッジで両方が更新される 2 つの信号を考えてみましょう:

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= x;
    b <= y;
  end if;
end process;
```

デルタサイクルがなければ、シミュレータは任意の順序を選ばなければなりません — `a` は `b` より先に更新される? 後? まったく同じ瞬間に? デルタサイクルはこれを回避します: 両方の代入は δ₀ でスケジュールされ、両方が δ₁ で有効になります。`a` または `b` を読むプロセスは、両方の新しい値を同時に見ます。

## 競合条件の罠

これを見てください:

```vhdl
process(a)
begin
  b <= a;
end process;

process(b)
begin
  c <= b;
end process;
```

`a` が変化すると、最初のプロセスが発火し `b` をスケジュールします。δ₁ で `b` は新しい値を持ちます。2 番目のプロセスが発火し、`c` をスケジュールします。δ₂ で `c` は正しい値を持ちます。

さて、2 つのプロセスを入れ替えてみてください。何か変わりますか? **いいえ。** デルタサイクルは、ファイル内のプロセスの「順序」が異なっても、両方の経路が同じ最終結果を生むことを保証します。まさにそれがデルタサイクルが存在する理由です。

## どこで問題になるか

問題は **信号** セマンティクスと「同じティック内でこれがあれより先に起きてほしい」を混ぜ合わせるときです。例:

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= b + 1;     -- a はティックの終わりに更新
    b <= a + 1;     -- b は古い a を読む
  end if;
end process;
```

「1 行目が先に実行されるので、2 行目が実行されるときには `a` はすでに更新されている」と仮定したなら、間違っています。`a` はティックの終わりに更新されます。`b` は `a` の古い値を読みます。結果: 両方ともお互いの新しいデータではなく、古いデータに基づいてインクリメントされます。

C スタイルのセマンティクスを得るには信号を変数で置き換えます:

```vhdl
process(clk)
  variable aa, bb : integer;
begin
  if rising_edge(clk) then
    aa := bb + 1;   -- 即座
    bb := aa + 1;   -- 新しい aa を見る
  end if;
end process;
```

これでソフトウェアプログラマが期待する通りに動きます。

## 要点

- デルタサイクルはシミュレータが並行ロジックを決定的にする方法。
- 信号代入はデルタサイクルの **後に** 有効になる。変数は違う。
- テストベンチがクロックエッジ付近で「奇妙」に振る舞うなら、ツールを責める前にデルタサイクルの順序問題を疑いましょう。
