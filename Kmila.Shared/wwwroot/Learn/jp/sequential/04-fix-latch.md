# 修正:意図せず推論されたラッチ

これは、どの VHDL 学生も少なくとも一度は書くバグの、2 つか 3 つのうちの一つだ。紙の上では正しく見え、エラーなくビルドでき、それらしい出力でシミュレートされ — そして合成すると、ツールが頼んでもいない **ラッチ** を推論したと警告してくるのだ。

皮肉なのは、第 IV 単元ではラッチ(SR、D)を *意図的に* 作ることを教える点だ。ここで身につけるべき技術は、純粋な組合せ論理であるはずのものの中に、**うっかり** ラッチを作ってしまったことを見抜くことだ。

## 出発点

```vhdl
architecture rtl of latch_bug is
begin
  process(enable, a, b)
  begin
    if enable = '1' then
      y <= a and b;
    end if;
    -- 抜け:enable = '0' のとき y はどうあるべき?
  end process;
end architecture rtl;
```

## 何がうまくいかないか

純粋な組合せ process では、すべての出力が process を通る **すべての経路で** 代入されなければならない。これは `enable = '1'` のときにしか `y` を代入していない。`enable = '0'` のとき、process は `y` について何も言わない。

「この信号をどうすればいいか言ってくれなかった」に対する VHDL の答えは、**前の値を保つ** だ。前の値を保てるハードウェアはメモリ素子だけなので、合成は **透過ラッチ(transparent latch)** を推論する。それはまさに D ラッチだ。`enable = '1'` の間は出力が `a and b` に追従し、`enable` が落ちると最後の値が凍結される。あなたはゲートを頼んだのに、イネーブル付きのラッチを得たのだ。

## うっかりラッチがなぜ悪いか

ラッチが悪というわけではない — *意図しない* ラッチが設計を台無しにするのだ。

- **タイミングクロージャが難しくなる。** 静的タイミング解析は透過ラッチを苦手とする。ほとんどの FPGA フローはエッジトリガのフリップフロップを前提としており、推論されたラッチをもっともな理由で警告として扱う。
- **グリッチが通り抜ける。** 透過している間、`a` や `b` の上のあらゆるグリッチが `y` へまっすぐ流れ、ラッチされ得る。
- **シミュレーション / 合成の不一致のリスク。** 振る舞いは、間違えやすい微妙な代入のカバレッジに依存する。

だから、ツールが「信号 `y` にラッチを推論しました」と言ったら、無視してよい警告ではなく、直すべきエラーとして扱おう。

## あなたのミッション

サンプルを開き、設計を **純粋に組合せ的** に — ラッチなし、フリップフロップなし、ただのゲート — にしよう。定石の修正が 2 つある。

**修正 1:先頭での既定代入**

```vhdl
process(enable, a, b)
begin
  y <= '0';                       -- 既定:すべての経路をカバーする
  if enable = '1' then
    y <= a and b;
  end if;
end process;
```

1 つの信号は、1 回の process 実行で何度も代入できる — 実行された最後の 1 つだけが効力を持つ。先頭の既定値は「下で何かが私を上書きしない限り、`'0'` であれ」という意味だ。これはスケールする習慣だ。まず既定を設定し、それから上書きするのだ。

**修正 2:`if` を完成させる**

```vhdl
process(enable, a, b)
begin
  if enable = '1' then
    y <= a and b;
  else
    y <= '0';                     -- 抜けていた分岐
  end if;
end process;
```

どちらも正しい。どちらも同一のハードウェア(`enable` でゲートされた 2 入力 AND、無効時は出力 `'0'`)を生成する。読みやすいと思うほうを選ぼう。

## `case` の中の同じ罠

ラッチは `if` だけの問題ではない。不完全な `case` や、ある分岐で出力を忘れた `case` も、ラッチを推論する。

```vhdl
-- バグ:sel = "10" と "11" で 'y' が未代入
case sel is
  when "00" => y <= a;
  when "01" => y <= b;
  when others => null;   -- null は何も代入しない -> y にラッチ
end case;
```

治療法は同じだ。`case` の前に `y` へ既定値を与えるか、`when others` で(そしてすべての分岐で)代入しよう。`process(all)` は *感度リスト* の誤りを避ける助けにはなるが、カバレッジの誤りからは **救ってくれない** — すべての経路ですべての出力を代入するのは、やはりあなたの仕事だ。

## 修正を検証する

修正したら、シミュレーションを実行しよう。波形で:

- `15–25 µs`(`enable = '1'` かつ `a = b = '1'` のとき):`y = '1'`。
- それ以外のすべての時刻:`y = '0'`。

修正前は、`enable` が `'0'` に戻っても `y` は `'1'` のまま留まった — それがラッチが前の値を保持している様子で、まさに避けたいものだ。

## 覚えておくべきこと

- 組合せ process では、**すべての出力をすべての経路で代入** しなければならない — 経路を取りこぼす `if` / `case` は透過ラッチを推論する。
- process の先頭での既定代入が、カバレッジを保証する最も簡単な方法だ。
- *うっかり* ラッチはタイミングとグリッチの問題を起こす。*意図的な* もの(D / SR ラッチ)は第 IV 単元の意識的な設計上の選択だ。
- `process(all)` は感度リストを直すのであって、代入のカバレッジは直さない — すべての出力を代入するのはやはりあなたの仕事だ。
- 本当にメモリが欲しいなら、それを忍び込ませてはいけない — クロック付き process へ移り、その決定を自分のものにしよう。
