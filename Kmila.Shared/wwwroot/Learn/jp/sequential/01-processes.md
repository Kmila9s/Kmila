# プロセス(process)と感度リスト

VHDL で process の外にあるものはすべて並行だ — 線とゲートだ。回路に 1 クロックサイクルから次のサイクルへ **何かを覚えて** おきたくなった瞬間、process に手を伸ばす。process は HDL の単元に出てくる「順次文(sentencias secuenciales)」が住む場所であり、組合せ論理(第 III 単元)からメモリ素子(第 IV 単元)への橋渡しだ。

## process とは何か

`process` は、VHDL の architecture 内にある順次コードのブロックだ。その行は、ソフトウェアとまったく同じように上から下へ読まれる。しかし process そのものは、その **感度リスト(sensitivity list)** にある何かが変わったときだけ「動く」 — このリストが、process の目覚めの条件だ。

```vhdl
process(clk, reset)
begin
  if reset = '1' then
    q <= '0';
  elsif rising_edge(clk) then
    q <= d;
  end if;
end process;
```

このブロックの意味はこうだ。「`clk` か `reset` が変わるたびに、私の本体を再評価せよ。」それらのイベントの合間、process は眠り、`q` はその値を保つ — これはまさにレジスタの振る舞いだ。

## 99% の場面で見かける 2 つの形

### 組合せ process

感度リスト = 内部で **読まれるすべての信号**。クロックなし。出力は入力の純粋な関数だ。

```vhdl
process(a, b, sel)
begin
  if sel = '0' then
    y <= a;
  else
    y <= b;
  end if;
end process;
```

2 対 1 mux に合成される。記憶はない — ただし、すべての出力がすべての経路で代入されていることが条件だ(詳しくはラッチの修正演習で)。

### クロック付き(順次)process

感度リスト = 非同期リセットなら `(clk, reset)`、同期リセットなら `(clk)` だけ。データの代入は `rising_edge(clk)`(または `falling_edge`)の中だけで起こる。出力は **レジスタ化** されており、クロックエッジでのみ変わる。

```vhdl
process(clk, reset)
begin
  if reset = '1' then
    q <= (others => '0');
  elsif rising_edge(clk) then
    q <= d;
  end if;
end process;
```

これが古典的な D フリップフロップのパターンであり、これから書くことになる本質的にすべてのレジスタの雛形だ。

## `rising_edge` と古い `clk'event` イディオム

クロックエッジを検出する方法は 2 つ見かける。

```vhdl
elsif rising_edge(clk) then        -- 推奨
elsif clk'event and clk = '1' then -- 古い、'0'/'1' については等価
```

`rising_edge(clk)`(`std_logic_1164` 由来)は、現代的で分かりやすい形だ。これはメタ値を含むエッジ(たとえば `'X'` → `'1'`)も正しく無視するが、生の `clk'event and clk='1'` はそれらで誤動作することがある。`rising_edge` を使おう。

## 感度リストの罠

*組合せ* の本体が読む信号をリストに入れ忘れると、シミュレーションと合成が食い違う。

- **シミュレーション**:その信号が変わっても process は再評価しない。波形は間違って見える(出力が「固まった」ように見える)。
- **合成**:ツールは本体を読み、すべての読みを見て、あなたのリストを無視して正しいハードウェアを構築する。

結果:テストベンチとボードの振る舞いが異なる。これは最悪の種類のバグだ。(クロック付き process はこの特定の罠には免疫がある。クロックエッジでしか動かないからだ。しかし *組合せ* process の不完全なリストは、幻のような失敗の古典的な原因だ。)VHDL-2008 は `process(all)` でこれを完全に解決する。

```vhdl
process(all)  -- ツールが本体で読まれるすべての信号を含める
begin
  ...
end process;
```

Kmila のパーサは `process(all)` を受け付けるし、新しい設計の組合せ process ではほとんどのチームがこれを使う。

## 経験則

- 感度 = `(clk)` か `(clk, reset)` だけ → あなたは **レジスタ**(フリップフロップ)を記述している。
- 感度 = 読むすべての入力(または `all`)→ あなたは **組合せ論理** を記述している。
- 感度にクロックエッジと、エッジの *外で* 使う余分なデータ信号が混在 → ほぼ確実にバグがある。

## もう一つ:同じ信号を 2 つの process から駆動しない

process の中で駆動される信号は、その process を自分のドライバとする。もし *2 つ目の* process(または並行文)もそれを駆動すると、複数ドライバを作ってしまう — `std_logic` なら `'X'` に解決され、解決されない型ならコンパイルエラーだ。各信号には、ちょうど 1 つのドライバを与えよう。

## 覚えておくべきこと

- process は、それ以外は並行であるファイルの中にある、順次コードの単位だ。
- クロック付き process(`rising_edge(clk)`)はフリップフロップに合成される — これがメモリを得る方法だ。
- `clk'event and clk='1'` より `rising_edge(clk)` を好もう。
- 組合せ process が読む信号はすべてリストに入れるか、`process(all)` を使おう。不完全なリストはシミュレーションと合成を食い違わせる。
- 1 つの信号に、1 つのドライバ。
