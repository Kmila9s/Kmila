# 並行代入:`when/else` と `with/select`

VHDL の組合せ論理は、並行文で書く — process の外にあるすべての行は、恒久的に配線されたハードウェアの一部を記述する。同じ仕事に対して 2 つの構文の流儀がある。**条件付き(conditional)** 代入(`when/else`)と **選択(selected)** 代入(`with/select`)だ。これらは HDL の単元に出てくる「並行文(sentencias concurrentes)」であり、コースに出てくるあらゆる組合せ回路 — 加算器、コード変換器、比較器、マルチプレクサ、エンコーダ、デコーダ — の屋台骨だ。

## `when/else` — 条件付き

優先順位の付いた条件のリストがあるときや、各分岐が *異なる* 信号を調べるときに向いている。

```vhdl
y <= (others => '0') when reset = '1' else
     a               when sel = "00"  else
     b               when sel = "01"  else
     c               when sel = "10"  else
     d;
```

最初に一致した条件が勝つ。順序が重要だ — これは **優先度 mux(priority mux)** にコンパイルされ、一番上の条件が `y` への最も直接的な経路を持つ。なお、すべての値の式(`a`、`b`、`c`、`d`、全ゼロのアグリゲート)は `y` と **同じ型かつ同じ幅** でなければならず、最後の `else` には条件がない — これがすべてを受け止めるキャッチオールだ。

## `with/select` — 選択

単一の式で切り替えるとき(ソフトウェアの `switch` / `case` 文のように)に向いている。

```vhdl
with sel select
  y <= a   when "00",
       b   when "01",
       c   when "10",
       'Z' when others;
```

すべての選択肢は同じ式(`sel`)と比較され、分岐は `else` ではなく **カンマ** で区切られ、`when others` は起こりうるすべての値を網羅するために **必須** だ。このスタイルは **バランスのとれた mux(balanced mux)** にコンパイルされ、どの分岐も特別扱いされない。

### なぜ `when others` は交渉の余地がないのか

ここでの `sel` は `std_logic_vector(1 downto 0)` だ。これなら 4 つのケース — `"00"`、`"01"`、`"10"`、`"11"` — だと思うだろう。しかし各ビットは *9 値* の `std_logic` なので、コンパイラは 9² = 81 通りの可能なパターン(`"0X"`、`"ZU"` など)を数える。それらを列挙することはできないので、文を網羅的にするために `when others` が必要なのだ。合成ではメタ値は消え去り、意図したとおりのきれいな 4 分岐 mux が得られる。

バー演算子で選択肢をまとめることもできる。

```vhdl
with opcode select
  result <= a + b    when "000" | "001",   -- 2 つのコード、同じ出力
            a - b    when "010",
            (others => '0') when others;
```

## どちらを選ぶべきか

- **同じ信号、多くのパターン**(デコーダ、mux、コード変換器):`with/select` は真理値表のように読める。これを使おう。
- **異なる信号、優先度論理**(reset が enable に勝ち、enable が data に勝つ):`when/else`。自然に当てはまる。
- **合成の出力:** 現代の FPGA では、どちらもほぼ同じゲートを生成する。そのため、ソースレベルでより分かりやすい形を選ぶのがほとんどの場合で正解だ。本当に優先度が欲しいときだけ `when/else` に手を伸ばそう。そうでなければ、`with/select` は次に読む人へ「優先度なし」と伝えてくれる。

## ラッチの罠(予告)

どちらの形式も、`y` が **すべての** シナリオで最終的に代入されることを要求する。並行の `when/else` や `with/select` は、実際には `y` を未代入のまま残せない — 構文が最後の `else` / `when others` を強制するからだ。ところが **process の中の等価な if / case** は残せてしまい、*そこで* シンセサイザが最後の値を「覚える」ためにラッチを推論する。これはまず望んでいないことだ。これは順次回路の単元の修正演習で正面から出会うのと同じラッチの罠なので、出力をすべての経路で代入する習慣を保とう。

## 手早い具体例とのつながり:2 ビット比較器

コースに出てくる大小比較器は、`when/else` からそのまま出てくる。

```vhdl
-- gt/eq/lt は単一の std_logic 出力
gt <= '1' when unsigned(a) > unsigned(b) else '0';
eq <= '1' when a = b else '0';
lt <= '1' when unsigned(a) < unsigned(b) else '0';
```

独立した 3 つの並行文、3 つの比較器、すべてが同時に生きている。

## これが次に出てくる場所

このレッスンのすぐ後の 3-8 デコーダのサンプルで `with/select` を使い、加算器・比較器・mux の作業を通じて `when/else` を使う。どちらも VHDL の日常の糧だ。

## 覚えておくべきこと

- `when/else` = 条件付き、優先度あり、異なる信号も可 → 優先度 mux。
- `with/select` = 1 つのセレクタ、カンマ区切りの選択肢、`when others` 必須 → バランスのとれた mux。
- すべての値の分岐は、ターゲットの型と幅に一致しなければならない。
- 並行形式は出力を落とせないが、process ベースの `if` / `case` 版は落とせる — そこがラッチの忍び込む場所だ。
