# なぜ CPU をパイプライン化するのか?

前のトラックで作ったシングルサイクル 8 ビット CPU は動く — けれど、実ハードウェアで途方もなく重要な 1 つの次元で制限されている:**クロック周波数** だ。

## シングルサイクルの天井

シングルサイクル設計では、クロック周期は、最も長いクリティカルパスの命令が端から端まで伝播し終えるのに十分な長さでなければならない:フェッチ → デコード → レジスタ読み出し → ALU → メモリ → ライトバック、すべて組合せ的に。最も長い経路が 20 ns なら、最大クロックは 50 MHz。それで終わりだ。

## パイプライン化とは、その経路を分割すること

経路をレジスタで区切られた N 段に分ける:

```
  [IF] → [ID] → [EX] → [MEM] → [WB]
    ^      ^      ^       ^       ^
    +------+------+-------+-------+
         段間のレジスタ
```

クロックはもはや経路全体ではなく、最も長い *段* が完了するのに十分な長さでよくなる。5 段、各々およそ 4 ns なら 250 MHz のクロックになる。スループットは 1 命令 / 20 ns から 1 命令 / 4 ns へ — 概念上は、タダで **5 倍の高速化** だ。

パイプライン化が *改善しない* ものに注目しよう:1 つの命令単体のレイテンシだ。1 つの命令は相変わらず 5 段を通り終えるのに — およそ 20 ns、以前と同じ時間(各境界でのレジスタのセットアップ時間のぶん、実際にはほんの少し長い)— かかる。変わるのは、パイプが満たされれば *新しい* 命令がサイクルごとに 1 つ完了する、という点だ。1 台の車を速くしているのではない。1 人の作業者を組立ラインに変えているのだ。

## 段間のレジスタ

段と段の間のレジスタは、帳簿づけではない — それらが *パイプラインそのもの* だ。各レジスタは、下流の段がまだ必要とするすべて、つまり途中結果、デスティネーションレジスタ番号、ID でデコードされた制御信号を、ラッチする。それがなければ、段 N+1 は段 N の入力が計算の途中で変わるのを見てしまう。これらは、ESCOM のシラバス(単元 IV)が HDL で実装するよう求める「registros inter etapa」(段間レジスタ)だ。

## なぜ実際には 5 倍にならないのか

理想は、パイプが満たされれば **CPI = 1**(命令あたり 1 サイクル)だ。2 つのことがそれを削る:

1. **充填と排出。** 最初の命令は何かが完了する前に 5 段すべてを必要とするので、短いプログラムは起動コストを払う。長い実行では無視できるが、きついループではそうはいかない。
2. **ハザード** — 本当の税金であり、このモジュールの残りの主題だ。

## ハザード — その対価

3 種類の衝突があり、それぞれに固有の対処がある:

**構造ハザード** — 2 つの段が、同じサイクルに同じ物理リソースを欲しがる。古典的なケース:IF が命令を読みたいのに MEM がデータを読みたい、しかしメモリポートは 1 つしかない。対処:命令メモリとデータメモリを分ける(ハーバード分割)か、ポートを複製する。

**データハザード** — 命令 N+1 が、命令 N がまだライトバックしていない値を必要とする:

```
  ADD R1, R2, R3   -- 結果は EX の終わりに準備でき、WB で書き込まれる
  SUB R4, R1, R5   -- 1 サイクル後、自分の EX で R1 を必要とする
```

助けがなければ、SUB は *古い* R1 を読む。対処は **フォワーディング**(バイパスとも呼ぶ)だ:ALU の結果を、WB まで這っていってレジスタファイルから出てくるのを待つ代わりに、N の EX/MEM 出力から N+1 の ALU 入力へ直接回す。フォワーディングはほとんどのデータストールを消す — ただし、すべてではない。**ロードユースハザード** は手ごわいものだ:ロードの値は MEM の終わり、EX より 1 段 *後* まで手に入らないので、それを直後に使う命令は、どんなに良いフォワーディングがあっても **1 サイクルストール** しなければならない(バブルを挿入する)。

**制御ハザード** — 命令 N が分岐で、パイプラインは分岐を取るかどうか判明する前に N+1(そしてたぶん N+2)をすでにフェッチ済み。対処:

- **ストール / フラッシュ** — 分岐が解決するまでフェッチを凍結するか、間違った経路の命令を走らせ始めておいて、推測が外れたら潰す。分岐を早く(EX ではなく ID で)解決すれば、ペナルティは 1 バブルに縮む。
- **静的予測** — コンパイル時に常に一方に賭ける(例:「後方分岐は取る」はループをうまく捕まえる)。
- **動的予測** — 実行時に学習する。分岐のアドレスで索引される **2 ビット飽和カウンタ** のテーブルを使う。カウンタは予測を反転させる前に、*2 回* 連続で外す必要がある。だから 99 回取られて 1 回抜けるループは、すぐには気を変えない。カウンタが上側の 2 状態にあるときは「取る」、下側の 2 状態にあるときは「取らない」と予測し、取られた分岐ごとに取る側へ、そうでなければ取らない側へ少し寄せる。安価で、はるかに手の込んだ方式とほぼ同じくらいうまくいく。

このモジュールの以降のレッスンでは、カリキュラムの 8 ビット CPU 上で、フォワーディングから始めて 1 つずつ対処を実装する — ESCOM の進行、estructural → datos → bypassing/forwarding → riesgo de control に合わせている。

## 覚えておくべきこと

- パイプライン化は、**命令あたりのレイテンシ**(変わらない、むしろわずかに高い)を **スループット**(はるかに高い)と引き換えにする:理想の CPI → 1。
- クロックの高速化は、経路全体でも最も短い段でもなく、最も長い *段* で頭打ちになる。
- 段間レジスタはデータ *と* 制御を前へ運ぶ。それらが重ね合わせを安全にしているものだ。
- フォワーディングはほとんどのデータハザードを消すが、ロードユースの組は依然として 1 ストールを要する。分岐は、予測しなければフラッシュのコストがかかる — 2 ビット飽和カウンタが働き者の予測器だ。
- ハザードはサイクルを消費し、その緩和策はゲートを消費する。実際の CPU 設計とは、このトレードオフを大規模に行うことだ。
