# なぜ CPU をパイプライン化するのか?

以前のトラックのシングルサイクル 8 ビット CPU は動きます — しかし実ハードウェアで非常に重要な 1 つの次元で制限されています: **クロック周波数** です。

## シングルサイクルの天井

シングルサイクル設計では、クロック周期は最も長いクリティカルパスの命令が全行程を伝播するのに十分な長さでなければなりません: フェッチ → デコード → レジスタ読み出し → ALU → メモリ → ライトバック、すべて組合せ的に。最長経路が 20 ns なら、最大クロックは 50 MHz。それが全て。

## パイプライン化はそのパスを分割すること

パスをレジスタで区切られた N 個のステージに分割します:

```
  [IF] → [ID] → [EX] → [MEM] → [WB]
    ^      ^      ^       ^       ^
    +------+------+-------+-------+
         registers between stages
```

クロックはパス全体ではなく、最も長い *ステージ* が完了するのに十分な長さだけ必要になります。5 つのステージ、それぞれ約 4 ns で、250 MHz のクロックが得られます。スループットは 1 命令 / 20 ns から 1 命令 / 4 ns になります — 概念的には **5 倍高速** 、タダで。

## ハザード — コスト

実際には 5 倍は得られません。3 種類の衝突:

- **データハザード** — 命令 N+1 は命令 N がまだ書き込んでいるレジスタを読む。対策: フォワーディングパスやストールサイクル。
- **制御ハザード** — 命令 N は分岐で、実行するかどうかを知る前に N+1 をすでにフェッチしている。対策: 分岐予測かパイプラインフラッシュ。
- **構造ハザード** — 2 つのステージが同じ物理リソース(例: 1 つのメモリポート)を必要とする。対策: リソースを複製するか、直列化する。

このモジュールの後続のレッスンはそれぞれ、カリキュラムの 8 ビット CPU に対して一度に 1 つの対策を実装していき、フォワーディングから始めます。

## 覚えておくべきこと

- パイプライン化は **命令あたりのレイテンシ** (高くなる) を **スループット** (はるかに高くなる) と引き換えにする。
- クロック高速化は最短ステージではなく最長ステージに制限される。
- ハザードはサイクルを費やし、緩和策はゲートを費やす。実際の CPU 設計は大規模なこのトレードオフ。

*さらにレッスンが来ます — このモジュールは現在執筆中です。*
