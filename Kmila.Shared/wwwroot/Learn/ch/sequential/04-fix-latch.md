# 修复:意外推断出的锁存器

这是每个 VHDL 学生至少写过一次的那两三个 bug 之一。代码在纸面上看着没问题,编译没有错误,仿真出来的输出也像那么回事 —— 可当你综合它时,工具却警告说它推断出了一个你从没要过的**锁存器**。

讽刺的是,第四单元教你*有意*去搭锁存器(SR、D)。这里要练的本领,是认出你什么时候在本该是纯组合逻辑的东西里**意外**搭出了一个。

## 起步代码

```vhdl
architecture rtl of latch_bug is
begin
  process(enable, a, b)
  begin
    if enable = '1' then
      y <= a and b;
    end if;
    -- 缺少:enable = '0' 时 y 应该是什么?
  end process;
end architecture rtl;
```

## 哪里出错

在一段纯组合 process 里,每个输出在穿过 process 的**每一条路径**上都必须被赋值。这段只在 `enable = '1'` 时给 `y` 赋值。当 `enable = '0'` 时,process 对 `y` 什么都没说。

VHDL 对“你没告诉我拿这个信号怎么办”的回答是:**保持上一个值**。唯一能保持上一个值的硬件是存储元件 —— 所以综合推断出一个**透明锁存器**。那正是一个 D 锁存器:当 `enable = '1'` 时输出跟随 `a and b`;当 `enable` 掉下去时,最后那个值被冻住。你要的是一个门,拿到的却是一个带使能的锁存器。

## 为什么意外的锁存器是坏事

不是说锁存器邪恶 —— 是说一个*非预期*的锁存器会毁掉你的设计:

- **时序难以收敛。** 静态时序分析对透明锁存器很头疼;大多数 FPGA 流程假设的是边沿触发的触发器,并把推断出的锁存器当成一个有充分理由的警告。
- **毛刺会穿过去。** 在透明期间,`a` 或 `b` 上的任何毛刺都会径直流向 `y`,并可能被锁存下来。
- **仿真/综合不一致的风险。** 它的行为取决于微妙的赋值覆盖情况,很容易搞错。

所以当工具说“为信号 `y` 推断出锁存器”时,把它当成一个要修的错误,而不是一个可以无视的警告。

## 你的任务

打开示例,把设计改成**纯组合** —— 没有锁存器、没有触发器,只有门。两种符合习惯的改法:

**改法 1:顶部默认赋值**

```vhdl
process(enable, a, b)
begin
  y <= '0';                       -- 默认:覆盖每一条路径
  if enable = '1' then
    y <= a and b;
  end if;
end process;
```

一个信号可以在一趟 process 执行里被赋值多次 —— 只有最后一个执行到的生效。顶部的默认值意思是“除非下面有什么覆盖我,否则就是 `'0'`”。这是可扩展的习惯:先设默认,再做覆盖。

**改法 2:补完 `if`**

```vhdl
process(enable, a, b)
begin
  if enable = '1' then
    y <= a and b;
  else
    y <= '0';                     -- 那条缺失的分支
  end if;
end process;
```

两种都对。两种产生完全相同的硬件(一个由 `enable` 把门的 2 输入 AND,禁用时输出 `'0'`)。哪种读起来更好就挑哪种。

## `case` 里的同一个陷阱

锁存器不只是 `if` 的问题。一个不完整的 `case`,或者某个分支忘了给输出赋值,同样会推断出锁存器:

```vhdl
-- BUG:sel = "10" 和 "11" 时 'y' 没被赋值
case sel is
  when "00" => y <= a;
  when "01" => y <= b;
  when others => null;   -- null 什么都不赋 -> y 上出现锁存器
end case;
```

同样的解药:在 `case` 之前给 `y` 一个默认值,或者在 `when others` 里(以及每一个分支里)给它赋值。`process(all)` 帮你避开*敏感列表*的错误,但它**救不了**覆盖的错误 —— 你仍然得在每一条路径上给每一个输出赋值。

## 验证你的修复

修完之后跑仿真。在波形里:

- `15–25 µs` 期间(当 `enable = '1'` 且 `a = b = '1'`):`y = '1'`。
- 其它所有时间:`y = '0'`。

修复之前,当 `enable` 掉回 `'0'` 时 `y` 会一直保持 `'1'` —— 那正是锁存器在保持它的上一个值,恰好是你想避免的。

## 要点

- 在组合 process 里,**每个输出都必须在每一条路径上被赋值** —— 一个漏掉某条路径的 `if`/`case` 会推断出一个透明锁存器。
- 在 process 顶部放一个默认赋值,是保证覆盖的最简单办法。
- 一个*意外*的锁存器带来时序和毛刺问题;一个*有意*的(D/SR 锁存器)是第四单元里刻意的设计选择。
- `process(all)` 修的是敏感列表,不是赋值覆盖 —— 你仍然得给每一个输出赋值。
- 如果你真的想要记忆,就别让它偷偷溜进来 —— 换到一个时钟驱动 process,并对这个决定负责。
