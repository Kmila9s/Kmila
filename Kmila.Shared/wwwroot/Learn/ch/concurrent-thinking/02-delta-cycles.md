# delta 周期与竞争条件

仿真器必须给“同时发生的两件事”一个确定的顺序。VHDL 的回答是 **delta 周期**:一段无穷小的时间,它在不推动墙上时钟的前提下把因和果分开。它在 VHDL 标准的仿真周期里有精确定义,理解它能让那些“诡异的”测试台行为突然说得通。

## delta 周期是什么

仿真时间以真实步长前进(以 ns、µs、ms 为单位)。但在单个时间步内,变化按 **delta 周期**的顺序发生:

- δ₀:一条赋值调度一次信号更新。
- δ₁:更新生效;任何对那个信号敏感的 process 现在看到新的输入,于是被唤醒。
- δ₂:那些被唤醒的 process 调度*它们*自己的更新。
- δ₃:那些更新生效;可能有更多 process 被唤醒。
- …

每一个 delta 都是“零真实时间”,但仍代表一个因果步。仿真器不停地循环走 delta,直到没有任何信号再变化 —— 电路**稳定**了 —— 这时真实仿真时间才前进到下一个事件。

## 把仿真周期讲得更精确一点

引擎走一趟是这样的:(1) 把时间推进到下一个已调度的事件;(2) 更新所有被调度在当前这一刻的信号;(3) 把每一个正在等待这些信号之一的 process 运行到结束,这可能又调度出新的更新;(4) 如果其中有任何更新是针对*当前*时刻的,就再走一个 delta 周期,否则推进时间。第 2 步里的信号更新全都发生在第 3 步任何 process 读它们*之前* —— 这就是“信号在步末才更新”背后的机制。

## 为什么会有它

考虑两个在同一个时钟沿都更新的信号:

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= x;
    b <= y;
  end if;
end process;
```

没有 delta 周期的话,仿真器只能任选一个顺序 —— `a` 在 `b` 之前更新?之后?delta 周期绕开了这个问题:两条赋值都在 δ₀ 排好,都在 δ₁ 生效。任何读 `a` 或 `b` 的 process 同时看到两个新值。结果不再取决于仿真器碰巧按什么顺序去处理事情。

## 一条数据流链

```vhdl
process(a)
begin
  b <= a;
end process;

process(b)
begin
  c <= b;
end process;
```

当 `a` 变化,第一个 process 触发并调度 `b`。在下一个 delta,`b` 有了新值,这唤醒第二个 process,它调度 `c`。再下一个 delta,`c` 就对了。注意 `c` 要经过**两个 delta 周期**才追上 `a` —— 真实时间从没移动过,但因果关系按顺序被保住了。把文件里这两个 process 对调,什么都不会变:delta 的排序保证了相同的最终结果。这正是 delta 周期存在的原因。

## 竞争条件陷阱

问题出在你把 **signal** 语义和一个“在同一 tick 里这件事必须先于那件事”的假设混在一起:

```vhdl
process(clk)
begin
  if rising_edge(clk) then
    a <= b + 1;     -- a 在步末更新
    b <= a + 1;     -- b 读到的是旧的 a
  end if;
end process;
```

如果你以为“第 1 行先跑,所以第 2 行运行时 `a` 已经更新好了”,那你错了。两边的右端式都用**旧**值求值,然后两个结果都被调度。`b` 读到的是 `a` 的旧值,不是刚算出来的那个。

把 signal 换成 variable,就拿到 C 风格、写完立刻读得到的语义:

```vhdl
process(clk)
  variable aa, bb : integer;
begin
  if rising_edge(clk) then
    aa := bb + 1;   -- 立刻
    bb := aa + 1;   -- 看到新的 aa
  end if;
end process;
```

现在它就按软件程序员预期的方式工作了。(而且硬件也不同:signal 版本做出两个从旧寄存器取值的并行加法器;variable 版本做出一条有依赖关系的链。)

## 一个经典的真实 bug:被忘掉的时钟沿

delta 思维也解释了为什么下面这段测试台激励会出错:

```vhdl
clk  <= not clk after 10 ns;
-- 别处,在一个没有 wait 的 process 里:
data <= next_value;   -- 和 DUT 采样的那个沿在同一个 delta?
```

如果一个激励信号恰好在 DUT 打拍子的*同一个* delta 里变化,那么 DUT 看到的是旧值还是新值就很脆弱。修法是把激励变化安排在离有效沿*有一段安全余量*的地方(或者用 `wait until rising_edge(clk)` 再加一小段延迟)。很多“仿真能过,但那个顺序感觉像随机的”的报告,追根溯源都在这里。

## 在工具里看出 delta

GHDL(Kmila 驱动的引擎)和 GTKWave 都会暴露 delta 步 —— 一个信号在单个时间点上可能要经过好几个 delta 周期才涟漪到它的最终值。如果波形显示一个占据“零时间”的毛刺,你看到的是中间的 delta 值,不是真实硬件行为。

## 几条要带走的

- delta 周期是仿真器让并发逻辑变得确定、又不虚构假时间的方式。
- 信号赋值在当前 delta **之后**生效;variable 不会 —— 它们立刻生效。
- 右端式用*旧*信号值求值,然后被调度。
- 如果你的测试台在时钟沿附近表现“怪”,先怀疑 delta 排序问题,再怪工具。

## 要点

- 一个 delta 周期是零真实时间,但是一个因果步;仿真器一直走 delta 直到电路稳定,然后推进时间。
- 信号在 delta 之间更新(所以同一趟里你读到的是旧值);variable 立刻更新。
- 把测试台激励安排在离有效时钟沿远一点的地方,以避免竞争。
